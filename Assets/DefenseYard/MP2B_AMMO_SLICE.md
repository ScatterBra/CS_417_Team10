## Two intentional delivery modes

SCV_DefenseSupplyLink.DeliverAmmo remains the existing remote inventory button, using DEF_GameState.I and its serialized defenseAmmoPerBox. No intake proximity is required. DEF_WorkshopAmmoReceiver accepts a specific physical box. Optional DeliverPresentedAmmo confirms a presented item separately. The source scene, existing button bindings and teammate XR hierarchy remain intact.

Each runtime ledger unit has a unique monotonically increasing identity and optional physical representation. Workbench BindLedger reserves an existing unit; it never creates inventory. Remote selection prefers units without a representation, then eligible represented units in registration order. Held, claimed, inactive or consumed boxes are excluded. Missing/destroyed representations do not erase valid inventory: remote transfer can consume that unit once. No global object search is used for ammo retirement. Repair behavior remains Felix's original and is outside this correction.

Physical and remote commits share the same validation/claim/debit/credit/retirement transaction. All states commit before notifications; reentry and mutation through ammo APIs are blocked during notification and removal. Subscriber exceptions are isolated. Legacy LoadAmmo and SpendAmmo now use this lifecycle too.

Unbound legacy props are rejected. An explicitly configured SCV_CraftedItem.explicitLegacyLedger (or intentional BindLedger call) can associate a prop with an available unit in that exact ledger. Never infer a source from name, nearest object or global search. ResetAmmoInventory invalidates prior identities even for a same-count reset; old props remain unusable and cannot consume new inventory. Direct public count changes are legacy compatibility only: detected count discrepancies invalidate old identities; same-count reset intent requires ResetAmmoInventory. These runtime identities are not a save-game persistence system.
